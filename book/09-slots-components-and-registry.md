# Slots, components, and the registry

So far in this book we've looked at the pieces of nonux as if they
were ordinary parts of a kernel: a UART driver, a scheduler, a
memory allocator. Each one is. But in nonux every one of those
pieces is also a **component** — a self-contained module that
plugs into a named **slot** and can be swapped at runtime for a
different implementation of the same interface. The scheduler
chapter already hinted at this: the round-robin policy and the
fixed-priority policy are two different components that both fill
the `scheduler` slot, and one can replace the other while the
kernel is running.

This chapter is the first chapter of Part V (Framework basics),
and it answers three questions that the earlier chapters glossed
over. *What is a slot?* — the typed connection point in the
running composition. *What is a component?* — the registered
implementation behind a slot. *What is the registry?* — the
runtime data structure that knows about every slot, every
component, and every edge between them, and that lets you ask "what
is this kernel built out of right now?" and get a real answer.

By the end you should be able to read `framework/registry.h`,
follow the bootstrap walk that wires up `kernel.json` at boot, and
recognise the `NX_COMPONENT_REGISTER` macro every component in
the source tree uses. The next chapter (chapter 10) covers the
**Interface Definition Language** that turns each interface
into generated `*_call.h` / `*_dispatch.h` headers; chapter 11
covers what flows across the edges the registry tracks (channels,
IPC messages). This chapter sets up the vocabulary both of those
build on.

The relevant files in this repo:

- [`framework/registry.h`](../framework/registry.h),
  [`framework/registry.c`](../framework/registry.c) — the
  Component Graph Registry: slots, components, connections,
  change events, snapshots, the bounded change log.
- [`framework/component.h`](../framework/component.h),
  [`framework/component.c`](../framework/component.c) — the
  component lifecycle state machine, the `nx_component_ops`
  callback table, the `NX_COMPONENT_REGISTER` macro, and
  `nx_resolve_deps` which wires manifest dependencies to live
  slots at boot.
- [`framework/bootstrap.h`](../framework/bootstrap.h),
  [`framework/bootstrap.c`](../framework/bootstrap.c) — the
  `nx_framework_bootstrap()` function that runs once during
  boot to register every slot, register every component, bind
  components to slots, resolve dependencies, and walk the
  composition through `init` → `enable` in topological order.
- [`kernel.json`](../kernel.json) — the declarative file that
  says which component fills which slot. The single source of
  truth for the boot composition.
- [`gen/slot_table.c`](../gen/slot_table.c) — generated by
  `tools/gen-config.py` from `kernel.json`. Contains one
  `struct nx_slot` per binding plus a flat `nx_boot_slots[]`
  table that bootstrap walks.
- [`core/boot/linker.ld`](../core/boot/linker.ld) — declares
  the `nx_components` section that every
  `NX_COMPONENT_REGISTER` macro emits into. Bootstrap walks
  this section at boot to discover every linked-in component.
- [`components/sched_rr/sched_rr.c`](../components/sched_rr/sched_rr.c),
  [`components/sched_rr/manifest.json`](../components/sched_rr/manifest.json)
  — a concrete component, paired with its manifest.
- [`components/posix_shim/manifest.json`](../components/posix_shim/manifest.json)
  — a component with non-trivial declared dependencies (four
  required slots), used in this chapter as the canonical example
  of how dependency injection works.

## Terms you'll see

- **Component.** A self-contained kernel module that implements
  one **interface** (the scheduler interface, the char-device
  interface, the filesystem interface) and plugs into a named
  slot. Every component in nonux is a separate directory under
  `components/`, with a `manifest.json`, one or more `.c` files,
  and a `README.md`.
- **Slot.** A typed connection point in the running composition.
  Has a name (`"scheduler"`, `"vfs"`), an interface tag
  (`"scheduler"`, `"vfs"`), mutability and concurrency labels,
  and a pointer to its currently-bound component (which may be
  NULL if nothing fills the slot yet). The slot, not the
  component, is what other components hold a reference to —
  swapping a component means changing the slot's `active`
  pointer.
- **Interface.** A typed contract that components implement and
  slots demand. A `"scheduler"`-typed slot can only be filled
  by a component whose interface is `"scheduler"`. Interfaces
  are described in `interfaces/idl/*.json`; chapter 10 walks the
  IDL.
- **Connection.** A directed edge from one slot to another in
  the registry's graph. An edge from `posix_shim` to `vfs`
  records "the component bound in slot `posix_shim` depends on
  the component bound in slot `vfs`". Connections are how the
  registry knows the shape of the composition.
- **Manifest.** A `manifest.json` file in each component's
  directory. Declares the component's name, version, the
  interface it implements, and the slots it requires (depends
  on). Read by `tools/gen-config.py` and by
  `tools/validate-config.py`.
- **`kernel.json`.** The declarative configuration file at the
  repo root. Names every slot the boot composition needs and
  pairs each slot name with the component that should fill it.
  The single line `"scheduler": { "impl": "sched_priority" }`
  is what makes the fixed-priority component the one that's
  active when the kernel boots.
- **Component graph registry.** The in-kernel data structure
  that holds every registered slot, every registered component,
  and every connection edge between them. Defined in
  `framework/registry.{h,c}`. The single source of truth at
  runtime for "what is the kernel built out of right now?".
- **`nx_components` section.** A linker section. Every component
  emits a `struct nx_component_descriptor` into it through the
  `NX_COMPONENT_REGISTER` macro. The linker auto-creates
  `__start_nx_components` and `__stop_nx_components` markers.
  Bootstrap iterates from start to stop to discover every
  linked-in component without keeping a hand-maintained table.
- **Component descriptor.** A `struct nx_component_descriptor`.
  Static, const, emitted by `NX_COMPONENT_REGISTER`. Carries
  the component's name, the size of its private state struct,
  the offset of its embedded `deps` struct, the dependency
  table, and pointers to its ops tables.
- **Component instance.** A `struct nx_component`. Allocated by
  the framework at boot, one per descriptor. Carries the
  component's instance ID, current lifecycle state, the
  pointer to its private state (`impl`), and a back-pointer to
  its descriptor.
- **Lifecycle state.** A component is always in exactly one of
  six states: `UNINIT`, `INIT`, `READY`, `ACTIVE`, `PAUSED`,
  `DESTROYED`. Transitions go through the verbs
  `nx_component_init` / `_enable` / `_pause` / `_resume` /
  `_disable` / `_destroy`. Illegal transitions are rejected.
- **Dependency injection.** Each component declares its
  dependencies in `manifest.json`. The build pipeline turns the
  manifest into a typed `struct <name>_deps` (one slot pointer
  per dep). At boot, the framework looks up each declared slot
  by name and writes the slot pointer into the component's
  state struct. The component never names a slot by string at
  runtime — its handle is the typed pointer.
- **Topological order.** The order bootstrap brings components
  up so that no component is enabled before its required
  dependencies are. If A depends on B, B is enabled first.
  Bootstrap uses Kahn's algorithm in a bounded O(n²) loop;
  cycles are reported as `NX_ELOOP`.
- **Change event.** A record emitted by the registry every
  time the composition mutates: a slot is registered, a
  component is bound to a slot, a connection is added, a
  component's lifecycle state changes. Events fire synchronously
  to subscribers and also land in a bounded ring buffer.
- **Snapshot.** A frozen copy of the registry's contents at a
  single generation number. Once taken, it is stable even if
  the registry mutates underneath. Used by the test harness,
  by `make verify-registry`, and (eventually) by an AI agent
  asking "what does this kernel look like right now?".

## A quick analogy first

A motherboard has labelled slots — RAM slots, PCIe slots, an
M.2 slot — and each slot accepts only a particular kind of
component. You can pull the GPU out of a PCIe slot and put a
different GPU in, as long as the new card fits the slot's
interface. The motherboard itself doesn't know which GPU is
plugged in; it just has a slot, and whatever's currently in
the slot is what gets talked to.

That's almost exactly the picture for nonux's framework. The
kernel has slots — `scheduler`, `vfs`, `char_device.serial`,
`memory.page_alloc` — and each slot has a typed interface. A
component fits a slot if its interface matches. At boot, every
slot has one component in it. At runtime, you can swap one
component for another (chapter 14 covers this) without restarting
anything. The thing other components hold onto is the slot, not
the component — so when the swap happens, every reference
automatically resolves to the new implementation.

The analogy stops working when you ask about the connections
between components. Motherboard traces are baked in. nonux's
connections are first-class registry data; the registry knows
that the `posix_shim` component depends on the `vfs` slot,
and that the `vfs` slot's bound component talks to the
`filesystem.root` slot. That's how you can ask "what does this
kernel look like right now?" and get a real graph back.

## What's actually in `kernel.json`

The boot composition is one short JSON file. Here is the file
[as it stands in the repo](../kernel.json), simplified by
removing the (currently empty) `connections` and `hooks`
sections:

```json
{
  "target": "aarch64-qemu-virt",

  "components": {
    "char_device.serial": {
      "impl": "uart_pl011",
      "config": { "base_addr": "0x09000000" }
    },
    "scheduler": {
      "impl": "sched_priority",
      "alternatives": ["sched_rr"],
      "config": {}
    },
    "memory.page_alloc": { "impl": "mm_buddy", "config": {} },
    "filesystem.root":   { "impl": "ramfs",    "config": {} },
    "filesystem.proc":   { "impl": "procfs",   "config": {} },
    "vfs":               { "impl": "vfs_simple", "config": {} },
    "posix_shim":        { "impl": "posix_shim", "config": {} }
  }
}
```

The keys of the `"components"` object are **slot names**. The
`"impl"` field of each entry is the **component** that fills
that slot at boot. So this composition has seven slots, each
filled by a named component.

Two slots are doing something subtle:

- `char_device.serial` and `filesystem.root` are not just
  interface names — they are *qualified* slot names. Read them
  as "the char_device slot called `serial`" and "the
  filesystem slot called `root`". A future composition that
  adds a second serial port would add `char_device.serial2`
  with the same `char_device` interface. The slot name
  individuates; the interface tag (which `gen-config.py`
  pulls from the manifest) types.
- `scheduler` carries an `"alternatives"` array. Both
  `sched_priority` and `sched_rr` get compiled in and
  registered; only `sched_priority` is bound to the slot at
  boot. The other one sits in lifecycle state `READY`, ready
  to be swapped in. This is the wiring chapter 8 referred to
  as "the dual-scheduler `kernel.json` build".

`kernel.json` is **declarative**. It says *what* the
composition is, not *how* to build it. The build pipeline
turns it into C. The compiled kernel does not parse
`kernel.json` at boot — it consumes the generated tables.

### What the build does with `kernel.json`

Three generated files do the work:

1. `gen/slot_table.c` — one `static struct nx_slot` per slot
   name, plus the flat `nx_boot_slots[]` array that pairs each
   slot with its desired component (by name string). Bootstrap
   walks this table to register every slot at boot.
2. `gen/<component>_deps.h` — for every component that
   declares dependencies in its manifest, a typed `struct
   <name>_deps` with one `struct nx_slot *` field per declared
   slot, plus a macro `<NAME>_DEPS_TABLE(CONTAINER, FIELD)`
   that expands to a list of `nx_dep_descriptor` initialisers
   using `offsetof` for type-safe, compile-time offsets.
3. `gen/config.h` — small `#define`s for per-component
   numeric/string config (the `"config": { ... }` blocks in
   `kernel.json`).

We will look at the first two in detail later in this chapter.
The third is mostly a convenience for components that need a
build-time constant; chapter 10 returns to it in the context of
IDL-driven code generation.

> **Side note: why a separate JSON file instead of a `.c`
> table?** A C table would be perfectly correct. The reason
> to keep `kernel.json` separate is that it is the *one*
> file an external tool — `make verify-registry`,
> `make validate-config`, an AI agent assembling a custom
> kernel — needs to read or modify to talk about the boot
> composition. Hiding it inside a C source file would force
> tooling to either parse C or coordinate with the compiler.
> JSON is the lowest-friction interchange format that
> survives "an AI agent edits the kernel". This is the
> same argument that made the per-component manifests JSON
> instead of, say, a C macro block.

## What a slot is — `struct nx_slot`

A slot is a small struct, defined in
[`framework/registry.h`](../framework/registry.h):

```c
struct nx_slot {
    const char              *name;        /* unique, e.g. "scheduler" */
    const char              *iface;       /* interface tag */
    enum nx_slot_mutability  mutability;
    enum nx_slot_concurrency concurrency;
    struct nx_component     *active;      /* NULL until something is bound */

    struct nx_slot          *fallback;
    _Atomic(enum nx_slot_pause_state) pause_state;
    struct nx_waitq         resume_waitq;
    _Atomic(uint32_t)        in_flight_calls;
};
```

(Eliding a couple of fields that only matter for the pause
protocol; chapter 14 walks those.)

Let's go field by field for the parts that matter now.

- **`name`** — a unique string. Slot lookup is by name:
  `nx_slot_lookup("scheduler")` returns the slot pointer.
  Names are caller-owned static storage (string literals
  emitted into `gen/slot_table.c` for the boot composition).
  The registry stores the pointer; it does not copy or own
  the string.

- **`iface`** — the interface tag. A slot's interface is what
  the dispatcher uses to decide *which* generated
  `<iface>_dispatch.h` handler to route a message through.
  Chapter 10 covers the IDL that defines what each interface
  means.

- **`mutability`** — one of `NX_MUT_HOT`, `NX_MUT_WARM`,
  `NX_MUT_FROZEN`. Says whether the slot's binding may
  change at runtime. `HOT` means a live swap is allowed
  while the kernel is running (today every slot is `HOT`).
  `WARM` would mean "swap only at safe points";
  `FROZEN` would mean "the binding may not change after
  boot". The labels are wired in so chapter 14's live-swap
  story can refuse to swap a `FROZEN` slot. No `FROZEN`
  slots ship yet.

- **`concurrency`** — one of `SHARED`, `SERIALIZED`, `PER_CPU`,
  `DEDICATED`. Hints at how the slot's handler is allowed to
  be entered. Today's single-core, single-dispatcher kernel
  uses `SHARED` everywhere; the field exists for the SMP
  build to mark slots whose handler is OK with concurrent
  invocations.

- **`active`** — the most important field. The pointer to the
  component currently bound to this slot. `NULL` means "no
  component is in this slot yet". `nx_slot_swap(slot, comp)`
  is the one function that writes `active`.

  Note what `active` is *not*: it is not the thing the IPC
  router or a calling component holds. Calling components hold
  a pointer to the **slot**. The slot holds the **component**.
  Indirection is one level. That is how a swap of `active`
  is transparent to every existing caller.

- **`fallback`** — a pointer to another slot that should
  receive a message if this slot is paused and the connection
  policy is `NX_PAUSE_REDIRECT`. Empty for current
  compositions.

- **`pause_state`** — `_Atomic`. The slot is in one of four
  pause states: `NONE` (normal traffic), `CUTTING` (pause
  starting), `DRAINING` (waiting for in-flight messages),
  `DONE` (component is now paused). The router consults this
  on every send. Chapter 14 walks the pause protocol.

- **`resume_waitq`** and **`in_flight_calls`** — scaffolding
  that the IPC blocking-call wrapper and the drain step of
  the pause protocol read. Chapter 11 walks them in the
  context of synchronous IPC.

The mutability and concurrency labels are not enforced
runtime invariants today; they are *declared properties*
that the framework reads when it needs to reason about a
slot. Both `make verify-registry` and the swap-time checks
in `framework/config.c` consult them. The labels exist now
so that compositions can already say "this slot is hot-swappable"
or "this slot is single-CPU-only", and a future verifier
gains the ability to refuse violations without needing the
label format to change.

### Where slots come from at boot

A slot is a plain C struct. It can be created any number of
ways:

- The generated `gen/slot_table.c` declares one `static struct
  nx_slot` per kernel.json binding. These are the seven slots
  the running kernel boots with.
- A test fixture can declare one inline on its stack and call
  `nx_slot_register(&s)` directly.
- A component that wants to expose a sub-slot (for example,
  procfs creating a per-file slot — not done yet, but the
  registry permits it) could allocate its own slot
  dynamically.

The registry does not allocate slot storage. The caller does.
`nx_slot_register` only adds the caller-owned struct to the
registry's index and initialises a few of its fields
(`pause_state`, `resume_waitq`, `in_flight_calls`, `fallback`).
Everything else — `name`, `iface`, `mutability`, `concurrency`
— the caller fills in before calling register.

Lookup is by name:

```c
struct nx_slot *nx_slot_lookup(const char *name);
```

So the registration handshake is: caller fills in `name`,
`iface`, `mutability`, `concurrency`; calls `nx_slot_register`;
the registry remembers the pointer, indexes it by name, and
emits an `NX_EV_SLOT_CREATED` event.

## What a component is — `struct nx_component` and the descriptor

A component has two parts in nonux: a **descriptor** and an
**instance**.

The **descriptor** is a `const struct nx_component_descriptor`.
It is static, it is emitted by the `NX_COMPONENT_REGISTER`
macro at compile time, and it lives in the `nx_components`
linker section. There is one descriptor per
component-source-file. The descriptor describes a *kind* of
component: its name, its private state struct size, its
dependency table, its ops tables. Two instances of the same
component would share one descriptor.

The **instance** is a `struct nx_component`. It is dynamic
(allocated by the framework at boot), one per descriptor in
v1. It carries the per-instance bookkeeping: an `instance_id`
string, the current lifecycle state, the pointer to this
instance's private state buffer (`impl`), and a pointer back
to the shared descriptor.

Here are both definitions.

```c
struct nx_component_descriptor {
    const char                       *name;        /* manifest name */
    size_t                            state_size;  /* sizeof(container) */
    size_t                            deps_offset; /* offsetof(container, deps) */
    const struct nx_dep_descriptor   *deps;
    size_t                            n_deps;
    const struct nx_component_ops    *ops;
    const void                       *iface_ops;
};

struct nx_component {
    const char              *manifest_id; /* e.g. "sched_rr" */
    const char              *instance_id; /* unique within manifest_id */
    enum nx_lifecycle_state  state;

    void                                   *impl;        /* private state */
    const struct nx_component_descriptor   *descriptor;  /* ops / state_size */
};
```

The descriptor's `ops` and `iface_ops` are two different ops
tables for two different purposes:

- **`ops`** is the framework-facing **lifecycle table**:
  `init`, `enable`, `pause_hook`, `pause`, `resume`,
  `disable`, `destroy`, and `handle_msg`. These are the
  callbacks the framework calls during composition transitions
  and message delivery.
- **`iface_ops`** is the interface-specific operations table,
  cast based on the slot's `iface`. For a scheduler component
  this is `struct nx_scheduler_ops *`. For a future
  filesystem component it is a `struct nx_fs_ops *`.
  `iface_ops` is `void *` here so this header does not need
  to include every interface's header; consumers cast based
  on the slot.

The `state_size` and `deps_offset` deserve a closer look. They
exist so the framework can allocate the private state at boot
without knowing the component's struct shape:

- `state_size` is `sizeof(component_state_struct)` — the full
  size of the component's private state struct, including the
  embedded `deps` substruct.
- `deps_offset` is `offsetof(component_state_struct, deps)` —
  where inside the private state struct the deps substruct
  lives. The dependency-injection code in `nx_resolve_deps`
  uses this to write slot pointers into the right place.

Both fields are filled in by the `NX_COMPONENT_REGISTER`
macro using `sizeof` and `offsetof`, so they are compile-time
constants. The framework never asks the component "how big is
your state?"; it reads the descriptor.

### The `NX_COMPONENT_REGISTER` macro

Every component in nonux ends its main `.c` file with one
expansion of this macro (or one of its two variants for
no-deps and iface-ops cases). Here is the basic form,
from [`framework/component.h`](../framework/component.h):

```c
#define NX_COMPONENT_REGISTER(NAME, CONTAINER, DEPS_FIELD, OPS, DEPS_TABLE) \
    NX_COMPONENT_REGISTER_IFACE(NAME, CONTAINER, DEPS_FIELD, OPS, NULL,    \
                                DEPS_TABLE)

#define NX_COMPONENT_REGISTER_IFACE(NAME, CONTAINER, DEPS_FIELD, OPS,      \
                                    IFACE_OPS, DEPS_TABLE)                  \
    static const struct nx_dep_descriptor NAME##_deps_tbl[] = {            \
        DEPS_TABLE(CONTAINER, DEPS_FIELD)                                  \
    };                                                                     \
    const struct nx_component_descriptor NAME##_descriptor                 \
        __attribute__((section("nx_components"), used)) = {                \
        .name        = #NAME,                                              \
        .state_size  = sizeof(CONTAINER),                                  \
        .deps_offset = offsetof(CONTAINER, DEPS_FIELD),                    \
        .deps        = NAME##_deps_tbl,                                    \
        .n_deps      = sizeof(NAME##_deps_tbl)                             \
                       / sizeof(NAME##_deps_tbl[0]),                       \
        .ops         = (OPS),                                              \
        .iface_ops   = (IFACE_OPS),                                        \
    }
```

Two things are happening here.

The macro emits a static array of dependency descriptors named
`<NAME>_deps_tbl` — one entry per declared dep. The contents
come from `DEPS_TABLE`, which is itself a macro defined in the
generated `gen/<name>_deps.h`. (We will look at this next.)

The macro emits a const `struct nx_component_descriptor` with
the `__attribute__((section("nx_components"), used))`
annotation. Two effects:

- **`section("nx_components")`** places the descriptor in the
  named section. The linker collects everything tagged that way
  into a contiguous range and emits the markers
  `__start_nx_components` and `__stop_nx_components` because
  the section name is a valid C identifier.

  The linker script `core/boot/linker.ld` reserves the section
  inside `.rodata`:

  ```
  __start_nx_components = .;
  KEEP(*(nx_components))
  __stop_nx_components = .;
  ```

  `KEEP` is the important word. Without it, `--gc-sections`
  would discard any descriptor that has no caller in the
  source — which is *every* descriptor, since the only place
  they are referenced is the linker markers themselves.

- **`used`** tells the compiler not to discard the symbol if
  it appears unused. Again, the descriptor has no direct
  caller; the framework finds it by walking the section.

The expansion is what lets bootstrap loop over every
linked-in component without anyone maintaining a "list of
components" file:

```c
for (const struct nx_component_descriptor *d = __start_nx_components;
     d < __stop_nx_components;
     d++) {
    /* register this component */
}
```

> **Side note: why a linker section instead of a registry
> macro?** A common pattern in other code bases is to have
> components add themselves to a registry at runtime via a
> constructor function. That works, but it requires
> constructor support (C++ static init, or a hand-rolled
> `__attribute__((constructor))` chain) and it leaves the
> ordering up to the linker's order-of-symbols rather than an
> explicit graph. The `nx_components` section approach gives us
> a stable, browsable, declarative list at link time — every
> descriptor that ended up in the kernel image is visible to
> `objdump -t kernel.elf | grep _descriptor`. Then bootstrap
> applies an explicit topological order, instead of relying on
> link order, which would silently break when someone
> rearranged `Makefile` rules.

The two variant macros handle the corner cases:

- `NX_COMPONENT_REGISTER_NO_DEPS(NAME, CONTAINER, OPS)` — for
  components with zero declared dependencies (uart_pl011,
  ramfs, the schedulers). Sets `deps = NULL`, `n_deps = 0`,
  `deps_offset = 0`. The component's state struct doesn't
  need an embedded `deps` field.
- `NX_COMPONENT_REGISTER_NO_DEPS_IFACE(NAME, CONTAINER, OPS,
  IFACE_OPS)` — same as above, plus the iface ops pointer.
  Used by the schedulers, which export
  `&sched_rr_scheduler_ops` (etc.) for the core driver to
  consume.

Concrete example, copying the last few lines of
[`components/sched_rr/sched_rr.c`](../components/sched_rr/sched_rr.c):

```c
const struct nx_component_ops sched_rr_component_ops = {
    .init       = sched_rr_init,
    .enable     = sched_rr_enable,
    .disable    = sched_rr_disable,
    .destroy    = sched_rr_destroy,
    .handle_msg = sched_rr_handle_msg,
};

NX_COMPONENT_REGISTER_NO_DEPS_IFACE(sched_rr,
                                    struct sched_rr_state,
                                    &sched_rr_component_ops,
                                    &sched_rr_scheduler_ops);
```

That single macro line produces a const descriptor in the
`nx_components` section named `sched_rr_descriptor`. The
framework will find it at boot, allocate one instance of
`struct nx_component` for it, allocate a buffer of
`sizeof(struct sched_rr_state)`, and run the lifecycle.

## Manifests and dependency injection

`NX_COMPONENT_REGISTER` works when the component's
dependencies are already known — that is, when the
`<NAME>_DEPS_TABLE` macro is defined somewhere the component
can `#include`. That somewhere is the generated
`gen/<name>_deps.h`, produced from the component's
`manifest.json`.

Here is `components/posix_shim/manifest.json`:

```json
{
  "name": "posix_shim",
  "version": "0.1.0",
  "iface": "posix_shim",
  "requires": {
    "vfs": {
      "version": ">=0.1.0",
      "mode": "async",
      "stateful": true,
      "policy": "queue"
    },
    "scheduler": {
      "version": ">=0.1.0",
      "mode": "async",
      "stateful": false,
      "policy": "queue"
    },
    "memory.page_alloc": {
      "version": ">=0.1.0",
      "mode": "async",
      "stateful": false,
      "policy": "queue"
    },
    "char_device.serial": {
      "version": ">=0.1.0",
      "mode": "async",
      "stateful": false,
      "policy": "queue"
    }
  }
}
```

Four required slots. Each entry says: the slot's name, the
version constraint, whether the link is async or sync, whether
the connection carries stateful semantics (in which case a
swap of either side must trigger an `on_dep_swapped` callback
so the components can resync), and the pause policy
(`queue` / `reject` / `redirect`) — what should happen to a
message sent to this slot while the slot is paused for a
recomposition.

`tools/gen-config.py` reads this manifest and emits
`gen/posix_shim_deps.h`. Excerpted here:

```c
struct posix_shim_deps {
    struct nx_slot *char_device_serial;
    struct nx_slot *memory_page_alloc;
    struct nx_slot *scheduler;
    struct nx_slot *vfs;
};

#define POSIX_SHIM_DEPS_TABLE(CONTAINER, FIELD)                        \
    { .name = "char_device.serial",                                    \
      .offset = offsetof(CONTAINER, FIELD.char_device_serial),         \
      .required = true, .version_req = ">=0.1.0",                      \
      .mode = NX_CONN_ASYNC, .stateful = false,                        \
      .policy = NX_PAUSE_QUEUE },                                      \
    { .name = "memory.page_alloc",                                     \
      .offset = offsetof(CONTAINER, FIELD.memory_page_alloc),          \
      .required = true, .version_req = ">=0.1.0",                      \
      .mode = NX_CONN_ASYNC, .stateful = false,                        \
      .policy = NX_PAUSE_QUEUE },                                      \
    { .name = "scheduler",                                             \
      .offset = offsetof(CONTAINER, FIELD.scheduler),                  \
      .required = true, .version_req = ">=0.1.0",                      \
      .mode = NX_CONN_ASYNC, .stateful = false,                        \
      .policy = NX_PAUSE_QUEUE },                                      \
    { .name = "vfs",                                                   \
      .offset = offsetof(CONTAINER, FIELD.vfs),                        \
      .required = true, .version_req = ">=0.1.0",                      \
      .mode = NX_CONN_ASYNC, .stateful = true,                         \
      .policy = NX_PAUSE_QUEUE }
```

Two things to notice.

First, the `struct posix_shim_deps` is **typed**. The
`vfs` field is a `struct nx_slot *`, not a string. The
component holds a *typed pointer* to the slot from the moment
its state is allocated. No string lookups at runtime.

Second, the `POSIX_SHIM_DEPS_TABLE` macro uses `offsetof`
into the *container* struct (the component's full state
struct) via the `FIELD` parameter that names where the
`deps` substruct is embedded. The component author embeds
the deps struct inside their state:

```c
struct posix_shim_state {
    struct posix_shim_deps deps;
    /* ... private state ... */
};
```

and then writes:

```c
NX_COMPONENT_REGISTER(posix_shim,
                      struct posix_shim_state,
                      deps,
                      &posix_shim_component_ops,
                      POSIX_SHIM_DEPS_TABLE);
```

The `deps` argument is the field name. The macro expansion
synthesises `offsetof(struct posix_shim_state, deps)` and
combines it with the per-field offsets from
`POSIX_SHIM_DEPS_TABLE` to produce a flat list of
`nx_dep_descriptor` entries, each carrying the offset
*from the container root* (not from the deps field) so the
framework can write directly into the state struct.

### `nx_resolve_deps`: how slot pointers get installed

At boot, after the slot table is registered and every
component is instantiated, the framework calls
`nx_resolve_deps` on each component:

```c
int nx_resolve_deps(const struct nx_component_descriptor *d,
                    struct nx_slot *self_slot,
                    void *state)
{
    if (!d || !state) return NX_EINVAL;

    for (size_t i = 0; i < d->n_deps; i++) {
        const struct nx_dep_descriptor *dep = &d->deps[i];
        struct nx_slot *tgt = nx_slot_lookup(dep->name);

        if (!tgt) {
            if (dep->required) return NX_ENOENT;
            continue;
        }

        struct nx_slot **field = (struct nx_slot **)
            ((char *)state + dep->offset);
        *field = tgt;

        int err = NX_OK;
        nx_connection_register(self_slot, tgt,
                               dep->mode, dep->stateful, dep->policy, &err);
        if (err != NX_OK) return err;
    }
    return NX_OK;
}
```

The loop has three pieces:

1. **Look up the dep's slot by name.** If it doesn't exist
   and the dep is required, return `NX_ENOENT`. (Optional
   deps that fail to resolve are skipped — `posix_shim` has
   none, but a more elaborate component could mark some
   dependencies optional in its manifest.)
2. **Write the slot pointer into the component's state.**
   `dep->offset` is the offset from the container root,
   computed at compile time by the `POSIX_SHIM_DEPS_TABLE`
   macro. After this assignment, `state->deps.vfs` points
   to the `vfs` slot. The component reads it as a typed
   pointer for the rest of its life.
3. **Register a connection edge.** From `self_slot`
   (the component's own slot — what the framework looked up
   while binding this component) to the dep's `tgt` slot.
   This is the edge `posix_shim → vfs`. The registry now
   knows the shape of the dependency graph.

Step 3 is the bit the registry's introspection depends on. A
component that talks to another component via a slot pointer
*and forgets to register an edge* would still function — the
calls would go through — but `make verify-registry` would
flag the missing edge, and `nx_graph_snapshot_to_json` would
omit it from the snapshot. Going through `nx_resolve_deps` is
how the registry stays in sync with the dependency reality.

## The component lifecycle

A component is always in exactly one of six states. Transitions
go through verbs, and illegal transitions are rejected.

```
    UNINIT ──init──► INIT ──►──┐
       │                       ▼
       └─────────────────────► READY ──enable──► ACTIVE
                                 ▲                  │
                                 │                  ▼
                   disable ──────┼──────pause──► PAUSED
                                 │                  │
                                 └──────────────────┘
                                         resume: PAUSED → ACTIVE
                                         disable: PAUSED → READY
                   destroy: READY → DESTROYED (terminal)
```

The six states:

- **`UNINIT`** — initial state on allocation.
- **`INIT`** — reserved for future asynchronous bring-up.
  Today's `nx_component_init` drives `UNINIT → READY` in a
  single step. The `INIT` state is legal-but-unused so that a
  future split into "kick off init" / "init finished" can be
  added without breaking the state matrix.
- **`READY`** — initialised but not running. Lifecycle ops
  table's `init` has run; `enable` has not.
- **`ACTIVE`** — the component is taking messages.
  `ops->enable` has run.
- **`PAUSED`** — temporarily quiesced for a recomposition.
  Reached through the pause protocol (chapter 14): cutoff →
  drain → `pause_hook` → `ops->pause`.
- **`DESTROYED`** — terminal. The component has been torn
  down and is no longer accessible.

The verbs are in [`framework/component.h`](../framework/component.h):

```c
int nx_component_init   (struct nx_component *c);  /* UNINIT → READY  */
int nx_component_enable (struct nx_component *c);  /* READY  → ACTIVE */
int nx_component_pause  (struct nx_component *c);  /* ACTIVE → PAUSED */
int nx_component_resume (struct nx_component *c);  /* PAUSED → ACTIVE */
int nx_component_disable(struct nx_component *c);  /* ACTIVE|PAUSED → READY */
int nx_component_destroy(struct nx_component *c);  /* READY  → DESTROYED */
```

Each verb does five things in order:

1. **Check the current state.** `nx_component_enable` returns
   `NX_ESTATE` unless the component is currently in `READY`.
   Similarly for the others. The matrix is checked from a
   helper function so a typo in a verb's "expected from"
   cannot silently bypass it.
2. **Fire the lifecycle hook chain.** Subscribers registered on
   `NX_HOOK_COMPONENT_ENABLE` / `_PAUSE` / `_RESUME` /
   `_DISABLE` run with a context carrying the proposed
   `(from, to)` pair. A hook returning `NX_HOOK_ABORT` causes
   the verb to fail with `NX_EABORT` *without* mutating
   state. Chapter 13 walks the hook system.
3. **Call the component's `ops->` callback** (`init`,
   `enable`, etc.). If the component returns non-zero, the
   verb returns that non-zero — the state stays where it
   was. So a failing `enable` leaves the component in
   `READY` and the framework can retry, recompose, or
   panic the boot as appropriate.
4. **Transition the registry state.** A single call to
   `nx_component_state_set` updates the `state` field, bumps
   the graph generation, and emits an
   `NX_EV_COMPONENT_STATE` event with the `(from, to)`
   pair. The state mutation is the *last* step, so an
   observer who sees the new state can trust the callback
   has run.
5. **Return `NX_OK`** if everything succeeded.

The five-step pattern is uniform across all six verbs. The
only verb with extra machinery is `pause`, which walks the
slot-side pause protocol between steps 3 and 4 — chapter 14.

## The Component Graph Registry

We have looked at the parts: slots, components, the
descriptor, the lifecycle. The **registry** is the data
structure that holds all of them together at runtime, in
[`framework/registry.c`](../framework/registry.c).

Internally it is three singly-linked lists keyed off three
node types:

- a list of `struct slot_node`, one per registered slot.
- a list of `struct component_node`, one per registered
  component instance.
- a list of `struct conn_node`, one per registered
  connection edge.

Each `slot_node` also keeps two per-slot edge lists
(`incoming` and `outgoing`) so that "who depends on this
slot" and "what does this slot depend on" are O(degree)
queries, not full table scans.

A single counter `g_generation` is bumped on every mutation.
The current generation number is a fingerprint of the
composition: "you and I are looking at gen 42; if it is
still 42 when we both finish reading, the graph did not
change underneath us".

### The mutation API

These are the only functions that change the registry state.

For slots:

```c
int nx_slot_register   (struct nx_slot *s);
int nx_slot_swap       (struct nx_slot *s, struct nx_component *new_impl);
int nx_slot_unregister (struct nx_slot *s);
```

For components:

```c
int nx_component_register  (struct nx_component *c);
int nx_component_unregister(struct nx_component *c);
int nx_component_state_set (struct nx_component *c, enum nx_lifecycle_state s);
```

For connections:

```c
struct nx_connection *nx_connection_register(struct nx_slot *from,
                                             struct nx_slot *to,
                                             enum nx_conn_mode mode,
                                             bool stateful,
                                             enum nx_pause_policy policy,
                                             int *err);
int nx_connection_retune    (struct nx_connection *c,
                             enum nx_conn_mode mode, bool stateful);
int nx_connection_unregister(struct nx_connection *c);
```

Every mutation does the same three steps:

1. Validate (caller-owned pointers, names, no dupes).
2. Allocate the internal node, link it into the global list
   and any per-slot lists, bump the generation.
3. Emit a change event (synchronously to subscribers; also
   appended to the change log ring buffer).

### Connection edges

A connection is a directed edge:

```c
struct nx_connection {
    struct nx_slot          *from_slot;   /* may be NULL */
    struct nx_slot          *to_slot;     /* required */
    enum nx_conn_mode        mode;
    bool                     stateful;
    enum nx_pause_policy     policy;
    uint64_t                 installed_gen;
};
```

For the `posix_shim` example we have been following,
`nx_resolve_deps` registers four edges:

- `posix_shim_slot → vfs_slot` (stateful, async, queue)
- `posix_shim_slot → scheduler_slot` (stateless, async, queue)
- `posix_shim_slot → memory.page_alloc_slot` (stateless, async, queue)
- `posix_shim_slot → char_device.serial_slot` (stateless, async, queue)

`from_slot` is allowed to be `NULL`, which marks a "boot" or
"external" entry edge. The first dispatch to a slot from the
boot code is one example; another would be an edge that
points from outside the registry's universe (a syscall
arriving from EL0). All four edges above have a real
`from_slot` because they originate from another registered
slot.

The pause policy on each edge is what the IPC router consults
when it tries to send a message into a paused slot:

- `NX_PAUSE_QUEUE` — park the message on a hold queue until
  the slot resumes.
- `NX_PAUSE_REJECT` — return an error to the sender.
- `NX_PAUSE_REDIRECT` — reroute to the slot's `fallback`,
  with a depth limit to cut loops.

For `posix_shim` every edge uses `QUEUE`. That is appropriate
for a userspace-facing component: a userspace `read()` should
not see spurious errors because the kernel happens to be
recomposing — it should wait for resume. A more
latency-sensitive component might choose `REJECT` (return
`EAGAIN` immediately) or `REDIRECT` (failover to an
alternate slot).

### Lookup and traversal

Lookup is by name (for slots) or by manifest+instance ID
pair (for components):

```c
struct nx_slot      *nx_slot_lookup     (const char *name);
struct nx_component *nx_component_lookup(const char *manifest_id,
                                         const char *instance_id);
```

Traversal walks the entire registry in whatever order the
internal lists are in (which is reverse-insertion order today
— but the registry promises no ordering and callers should
not rely on one):

```c
void nx_graph_foreach_slot      (nx_slot_cb       cb, void *ctx);
void nx_graph_foreach_component (nx_component_cb  cb, void *ctx);
void nx_graph_foreach_connection(nx_connection_cb cb, void *ctx);
```

Per-slot traversal walks just the edges incident on a slot:

```c
void nx_slot_foreach_dependent (struct nx_slot *s, nx_connection_cb cb, void *ctx);
void nx_slot_foreach_dependency(struct nx_slot *s, nx_connection_cb cb, void *ctx);
```

`dependent` walks the slot's incoming edges (who depends on
this slot). `dependency` walks the outgoing edges (what this
slot depends on). The recomposer's Kahn's-algorithm pause
order is built off these two functions; chapter 14 walks
that.

### Change events and the change log

Every mutation emits one event. Subscribers are called
synchronously, from inside the mutating function, so they
see the post-mutation state. Two consumption paths exist:

- **Live subscribers** — up to 16 registered callbacks, each
  called for every event. Used for instrumentation, the
  recomposer's invariant checker, and test watchers.

- **The change log** — a fixed-capacity ring buffer (256
  entries) of recent events. On overflow, the oldest entries
  are overwritten; the `total` count keeps growing. The log
  answers "what was the last few mutations?" without needing
  a subscriber active at the time they happened.

The event kinds are an enum:

```c
enum nx_graph_event_type {
    NX_EV_SLOT_CREATED = 1,
    NX_EV_SLOT_DESTROYED,
    NX_EV_SLOT_SWAPPED,
    NX_EV_COMPONENT_REGISTERED,
    NX_EV_COMPONENT_UNREGISTERED,
    NX_EV_COMPONENT_STATE,
    NX_EV_CONNECTION_ADDED,
    NX_EV_CONNECTION_REMOVED,
    NX_EV_CONNECTION_RETUNED,
};
```

Each event carries a `generation` and a `timestamp_ns`, plus
event-specific payload in a tagged union. The complete
runtime history (subject to the ring buffer's capacity)
answers the question "what mutations brought the kernel to
its current state?".

### Snapshots

A snapshot is a frozen copy of the registry at a single
generation. It is *not* a pointer into the live registry —
the snapshot allocates and owns its own arrays of
`struct nx_snapshot_slot`, `nx_snapshot_component`, and
`nx_snapshot_connection`. Once taken, the snapshot is stable
even if the registry mutates underneath.

```c
struct nx_graph_snapshot *s = nx_graph_snapshot_take();
/* ... do whatever with s ... */
nx_graph_snapshot_put(s);
```

Snapshots are reference-counted: `take` returns refcount 1;
each `retain` bumps it; each `put` decrements; the snapshot
is freed when the count reaches zero.

The string fields in the snapshot still point into the
caller-owned storage that the live registry references — the
slot's `name` string, the component's `manifest_id` — so the
caller must keep those strings alive for the duration of the
snapshot. For the boot composition this is always true,
because the strings are string literals emitted into
`gen/slot_table.c` and the manifests.

Snapshots serialise to JSON via `nx_graph_snapshot_to_json`,
which gives external tooling and AI agents a single read
operation to fetch the entire composition graph. This is one
of the foundations of the AI-operability promise the project
makes: an AI agent reasoning about the kernel never has to
parse C source — it can read a JSON snapshot of the running
composition.

> **Side note: why a separate snapshot type at all?** A
> simpler design would be to expose the live registry
> directly and tell callers "don't iterate during a
> mutation". That works for single-threaded host tests, but
> the kernel build will eventually have a recomposer kthread
> mutating the registry while other code (introspection,
> instrumentation, a debug-shell command) reads it. A
> snapshot decouples readers from writers cleanly: take a
> snapshot, the writer carries on, the reader walks at its
> own pace. The cost is a one-time allocation; the benefit
> is a stable, consistent view of the graph that does not
> drift under the reader's feet.

## Bootstrap: how the registry is filled at boot

`nx_framework_bootstrap()` in
[`framework/bootstrap.c`](../framework/bootstrap.c) is the
function that runs once during boot, after the PMM, IRQ, and
timer are up, and turns the static descriptors and the
generated slot table into a live registry. Let's walk the
function from top to bottom.

### Step 1: register every slot

```c
for (unsigned i = 0; i < nx_boot_slots_count; i++) {
    int rc = nx_slot_register(nx_boot_slots[i].slot);
    if (rc != NX_OK && rc != NX_EEXIST) return rc;
}
```

`nx_boot_slots[]` and `nx_boot_slots_count` come from the
generated `gen/slot_table.c`. After this loop, the registry
has seven `slot_node` entries — one per slot in `kernel.json`.
Each slot's `active` pointer is still `NULL`; no component is
bound yet.

`NX_EEXIST` is tolerated because slots may have been
pre-registered by an earlier path (a test fixture, for
instance) — re-registering a slot that is already in the
table is a benign no-op for bootstrap purposes.

### Step 2: walk the descriptor section, register one component per descriptor

```c
size_t n = (size_t)(__stop_nx_components - __start_nx_components);
if (n == 0) return NX_OK;

struct nx_component **comps = calloc(n, sizeof *comps);
if (!comps) return NX_ENOMEM;

for (size_t i = 0; i < n; i++) {
    const struct nx_component_descriptor *d = &__start_nx_components[i];

    struct nx_component *c = calloc(1, sizeof *c);
    c->manifest_id = d->name;
    c->instance_id = "0";
    c->descriptor  = d;
    if (d->state_size > 0) {
        c->impl = calloc(1, d->state_size);
    }

    nx_component_register(c);
    comps[i] = c;

    struct nx_slot *slot = find_slot_for(d);
    if (slot) {
        nx_slot_swap(slot, c);
    }
}
```

(Eliding the error-return boilerplate for clarity.)

This is the loop that walks every linked-in component
descriptor. For each one, bootstrap allocates a
`struct nx_component` instance, allocates the component's
private state buffer (`state_size` bytes, zero-initialised),
registers the instance in the registry, and looks up the
slot the kernel.json binding wants this component in.

`find_slot_for` is a small helper that walks
`nx_boot_slots[]` looking for an `impl_name` matching the
descriptor's name. If found, `nx_slot_swap` is called with
the new component — and the slot's `active` pointer now
points at this instance.

A descriptor that doesn't match any slot is still registered
as a component, just unbound. That is how an `alternatives`
component (like `sched_rr` when `sched_priority` is the
default) survives boot: it sits in the registry in state
`READY`, with no slot referencing it as `active`. A future
`nx_config_swap_component` call (chapter 14) can find it by
manifest ID and bind it.

### Step 3: topological order — `init`, then `enable`

```c
bool *visited = calloc(n, sizeof *visited);

size_t done = 0;
while (done < n) {
    bool progressed = false;
    for (size_t i = 0; i < n; i++) {
        if (visited[i]) continue;
        const struct nx_component_descriptor *d = &__start_nx_components[i];

        if (!deps_ready(d, comps, visited, n)) continue;

        struct nx_slot *self_slot = find_slot_for(d);
        nx_resolve_deps(d, self_slot, comps[i]->impl);
        nx_component_init(comps[i]);

        if (self_slot) {
            nx_component_enable(comps[i]);
        }

        visited[i] = true;
        done++;
        progressed = true;
    }
    if (!progressed) return NX_ELOOP;
}
```

This is Kahn's algorithm in a bounded O(n²) loop. n is small
(seven components in the current composition) and dependency
counts per component are small (0–4), so the cost is
negligible.

The inner loop scans every unvisited component. For each one
it asks `deps_ready`: "is every *required* dependency of this
component already visited (i.e. already through `init` and
`enable`)?" If yes, the component is ready to bring up:

1. **Resolve dependencies.** `nx_resolve_deps` writes the
   slot pointers into the component's `deps` substruct and
   registers each connection edge. After this call, the
   component holds typed pointers to every slot it depends
   on, and the registry's edge list knows about them.
2. **Initialise.** `nx_component_init` runs the lifecycle
   verb described earlier: `UNINIT → READY`, with the
   `ops->init` callback fired in the middle.
3. **Enable, if bound.** If the component is bound to a slot
   (i.e. `find_slot_for` returned non-NULL), call
   `nx_component_enable` to move it into `ACTIVE`. Unbound
   alternatives stay in `READY` for a later live swap.

The bookkeeping is the `visited[]` array; the loop terminates
when every component is visited.

The two failure modes:

- **A required dependency does not resolve.** A
  `manifest.json` lists a dep that no kernel.json binding
  provides. `nx_resolve_deps` returns `NX_ENOENT` and
  bootstrap propagates it. The caller (in `boot_main`) is
  expected to panic with the offending manifest's name.
- **A cycle exists in the required-dep graph.** No component
  is ever ready, so `progressed` stays false, and the outer
  loop terminates by returning `NX_ELOOP`. Today's
  compositions are all DAGs and gen-config refuses cycles
  upstream, but bootstrap holds the line at runtime as a
  belt-and-suspenders check.

### Step 4 (kernel-only): publish the scheduler and spawn the dispatcher

The very last thing bootstrap does, on the kernel build only,
is wire up the scheduler driver and spawn the dispatcher
kthread:

```c
#if !__STDC_HOSTED__
struct nx_slot *sched_slot = nx_slot_lookup("scheduler");
if (sched_slot && sched_slot->active &&
    sched_slot->active->descriptor &&
    sched_slot->active->descriptor->iface_ops) {
    const struct nx_scheduler_ops *sops =
        sched_slot->active->descriptor->iface_ops;
    sched_init(sops, sched_slot->active->impl);
}

nx_dispatcher_init();
#endif
```

This is the only place anything outside the framework holds
a pointer to a component instance directly. The core
scheduler driver needs to know which scheduler's ops table
to call from `sched_check_resched` (chapter 8), and that
pointer comes from the `iface_ops` field of the descriptor
of whatever component is currently bound to the `scheduler`
slot. On a live swap, the scheduler component's `enable`
hook re-publishes the pair so the core driver picks up the
new policy.

`nx_dispatcher_init` spawns the kthread that pumps the
per-slot message queues. From here on, the kernel is
fully composed: every slot is bound, every component is
`ACTIVE`, and the message machinery is live.

The booted kernel reports its composition via a one-line
`kprintf` from `boot_main`:

```
composition (gen=N, 7 slots, 7 components)
```

The `N` is `nx_graph_generation()`, which has been bumping
on every mutation since the very first `nx_slot_register`.
For the boot composition it lands around 30 — seven slot
registers, seven component registers, seven slot swaps, plus
the dep-resolution edges (`posix_shim` adds four, vfs_simple
adds two, the schedulers add zero), plus the
`init`/`enable` state transitions (two per component).

## A worked example: tracing `posix_shim` from manifest to ACTIVE

To make all the pieces concrete, let's trace what happens at
boot for the `posix_shim` component, end to end. The
generation numbers below are illustrative — the actual values
depend on insertion order and may differ.

**At link time.** The compiler has produced one
`posix_shim_descriptor` symbol from the `NX_COMPONENT_REGISTER`
expansion at the bottom of `components/posix_shim/posix_shim.c`,
emitted into the `nx_components` section. `tools/gen-config.py`
has produced two files: `gen/slot_table.c` (which contains
`nx_slot_posix_shim` with `impl_name = "posix_shim"`) and
`gen/posix_shim_deps.h` (which contains `struct
posix_shim_deps` and `POSIX_SHIM_DEPS_TABLE`). The
`POSIX_SHIM_DEPS_TABLE` macro got pulled into `posix_shim.c`
through `#include` and provided the deps table argument to
`NX_COMPONENT_REGISTER`. The descriptor's `n_deps` is 4.

**Boot starts.** `boot_main` brings up the PMM, IRQ, timer.
Then it calls `nx_framework_bootstrap`.

**Step 1: slot register.** Bootstrap walks `nx_boot_slots[]`.
The `posix_shim` slot is registered. The registry now holds a
slot_node for it; the slot's `active` is `NULL`. Generation
bumps. An `NX_EV_SLOT_CREATED` event is emitted.

**Step 2: component allocation and binding.** Bootstrap walks
the descriptor section. When it reaches `posix_shim_descriptor`,
it allocates a `struct nx_component`, sets its
`manifest_id = "posix_shim"`, `instance_id = "0"`,
`descriptor = &posix_shim_descriptor`, and allocates a
zero-initialised buffer of size `sizeof(struct
posix_shim_state)`. The instance is registered; an
`NX_EV_COMPONENT_REGISTERED` event fires. Then `find_slot_for`
finds the matching slot, and `nx_slot_swap` binds the
component to it. `slot->active` now points at this instance.
An `NX_EV_SLOT_SWAPPED` event fires.

**Step 3: topological resolution.** Bootstrap now needs to
bring `posix_shim` from `UNINIT` to `ACTIVE`. But first, it
needs the four slots `posix_shim` depends on to be `ACTIVE`
already. `deps_ready` returns false until `vfs`, `scheduler`,
`memory.page_alloc`, and `char_device.serial` have all
visited. Those components have no required deps of their
own, so they visit first.

When `posix_shim`'s turn comes, three things happen:

1. **`nx_resolve_deps` runs.** Four edges register, one per
   required dep. Generation bumps four times. Four
   `NX_EV_CONNECTION_ADDED` events fire. Inside
   `state->deps`, the four slot pointers are written —
   `state->deps.vfs` now points at the vfs slot,
   `state->deps.scheduler` points at the scheduler slot, and
   so on.

2. **`nx_component_init` runs.** The `ops->init` callback
   fires (a no-op for posix_shim — its state is set up by
   dep resolution, not by an init callback). The state
   transitions `UNINIT → READY`. An `NX_EV_COMPONENT_STATE`
   event fires.

3. **`nx_component_enable` runs.** The hook chain fires for
   `NX_HOOK_COMPONENT_ENABLE`; assuming no hooks veto, the
   `ops->enable` callback fires. The state transitions
   `READY → ACTIVE`. Another `NX_EV_COMPONENT_STATE` event
   fires.

`posix_shim` is now bound, active, with its four typed slot
pointers ready to use. Any code path inside `posix_shim` that
needs to talk to vfs reaches through `state->deps.vfs` — a
typed pointer to the slot, not a name lookup.

**Result.** The registry now has seven slots, seven
components (one per descriptor in the section), and however
many connection edges the dep resolution emitted (two from
vfs_simple, four from posix_shim, plus the schedulers'
zero — six total today). Generation has bumped roughly 30
times. A snapshot taken now is what `kprintf`'s "composition
(gen=N, 7 slots, 7 components)" describes.

## What the registry buys us

The registry could have been replaced, in principle, with a
handful of hand-written tables and a few `extern` symbols.
What does maintaining it explicitly buy?

- **A single point of truth.** Every part of the system that
  asks "what is the kernel built out of right now?" consults
  the registry. There is one answer.
- **Decoupled introspection.** `make verify-registry`
  produces build-time errors when the composition violates a
  verification rule (R2 / R4 / R9); it works on the graph,
  not on the source.
- **The basis for hot-swap.** Chapter 14's
  `nx_config_swap_component` needs to know every edge that
  references a slot in order to pause traffic before the
  swap, and gets that information from
  `nx_slot_foreach_dependent` and friends.
- **An AI-readable kernel image.** An AI agent that wants to
  build, debug, or modify a nonux composition can read the
  registry's JSON snapshot rather than parsing C source.
- **Test fixtures with full control.** A host-side test
  calls `nx_graph_reset()` between cases, fabricates a
  synthetic composition, exercises a code path, and tears
  down — all without touching real boot machinery.

The cost is the bookkeeping discipline: every mutation goes
through a mutation function, components do not poke at their
own state field (they call `nx_component_state_set`), slots
do not bind themselves (they go through `nx_slot_swap`).
That discipline is what every other framework feature — the
change log, the event subscribers, the snapshots,
`verify-registry` — leans on.

## A few extra things to know

- **The registry's slot/component storage is caller-owned.**
  The registry allocates only its own internal `slot_node`,
  `component_node`, and `conn_node` bookkeeping. The `struct
  nx_slot` and `struct nx_component` themselves live in the
  caller's static or heap-allocated storage. That is why
  `nx_graph_reset` only frees the internal nodes — the
  caller-owned structs may be on a test stack frame that has
  already gone out of scope.

- **`nx_slot_unregister` refuses if any edge references the
  slot.** Returns `NX_EBUSY` until every incoming and
  outgoing edge has been unregistered. There is no "unregister
  in any order" mode — callers must tear down the wiring
  before the slot. The registry's invariants depend on edges
  pointing only at live slots.

- **`nx_component_destroy` refuses if the component is
  bound.** Same idea, one level up. A component still in
  some slot's `active` cannot be destroyed; the slot must
  swap to a different component first (or unbind to `NULL`).

- **Generations bump even on errors that mutate.** A
  partial mutation that allocates a node and then fails on
  the second step would normally roll back; the registry's
  mutation functions are written to bump the generation only
  after they have committed.

- **The change log is bounded at 256 entries.** That is enough
  to cover the entire boot sequence (~30 events) with room
  to spare for a recomposition or two. A workload that
  generates events faster than they are consumed will lose
  the oldest entries; `nx_change_log_total` keeps
  monotonically increasing so a reader can detect the loss
  by comparing against `held`.

- **Subscribers are limited to 16.** There is no dynamic
  subscriber list. Production users (the recomposer's
  invariant checker, an instrumentation recorder, a test
  watcher) collectively fit in 16; if the limit becomes
  binding the constant in `registry.c` is the only thing to
  bump.

- **There is no garbage collector.** A component that
  reaches `DESTROYED` and is unregistered is gone from the
  registry's view; the framework does *not* free the
  component's `impl` buffer (because the framework doesn't
  know the buffer's lifetime semantics — a future
  refcount-aware variant might be tied to the descriptor's
  `state_size`). For the boot composition this is fine:
  components never destroy, so there is no leak to worry
  about. For tests, the test's `setUp` calls
  `nx_graph_reset` and the host runtime's heap reclaims the
  rest.

- **The registry is a single-writer model today.** The host
  build is single-threaded, and the kernel build serialises
  mutations through the recomposer (chapter 14). The
  `_Atomic` annotations on `pause_state` and
  `in_flight_calls` mean readers in IPC paths don't need
  locks even on SMP, but mutations are still
  one-at-a-time. A future multi-writer kernel would need
  short-critical-section locking around the mutation
  functions; the API is designed so that change can happen
  without rewiring consumers.
